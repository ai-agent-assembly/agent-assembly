## npm dist-tag reconciliation (separate concern, per campaign instructions)

- All 5 npm packages confirmed **published** at explicit `0.0.1-rc.7`
  (`npm view <pkg>@0.0.1-rc.7 version`, all 5 returned `0.0.1-rc.7`).
- `npm view @agent-assembly/sdk dist-tags`: `{alpha: 0.0.1-alpha.9.1, beta:
  0.0.1-beta.5, latest: 0.0.1-rc.5, rc: 0.0.1-rc.7}` — the `rc` dist-tag
  correctly points at rc.7; `latest` is stale at rc.5.
- Root cause (established during the release campaign, re-confirmed here):
  the `release-node.yml` dist-tag-move step authenticates with the static
  `NPM_TOKEN` GitHub secret, which is invalid/expired (`npm error E401`).
  This is the exact gap AAASM-4017's own closure comment flagged as a manual
  prerequisite when npm publish itself moved to OIDC.
- **No republish performed.** `NPM_TOKEN` was not read, printed, logged, or
  exposed at any point.
- Reused **AAASM-4994** (open since the rc.5→rc.6 transition, never
  resolved) rather than filing a new ticket — this is the same recurring
  defect class, now with a concrete root cause. Comment added recording
  rc.7's occurrence and the exact recovery action.
- **Smallest canonical recovery**, once the human rotates `NPM_TOKEN`: either
  re-run `release-node.yml`'s dist-tag step, or run
  `npm dist-tag add @agent-assembly/sdk@0.0.1-rc.7 latest` (+ the 4 runtime
  sub-packages) directly. No republish of any package version required.
- Until then, npm's default/bare-install channel is truthfully
  `CHANNEL_INCOMPLETE`; explicit-version and `@rc` installs are fully green
  (see matrix below).

### Repair attempt with a fresh `NPM_TOKEN` (2026-09-17, follow-up session)

A fresh `NPM_TOKEN` was made available via the process environment for a
repair attempt. Full ground truth pulled first, not assumed:

- All 5 packages' `latest` was stale, and worse than the sdk-only finding
  above suggested: the 4 `@agent-assembly/runtime-*` sub-packages' `latest`
  was frozen at `0.0.1-alpha.4` (never advanced since — `release-node.yml`'s
  dist-tag-repair step only ever targeted `@agent-assembly/sdk`, never the
  runtime sub-packages; low-impact in practice since they're consumed by
  exact-version `optionalDependencies` from the main package, not by their
  own dist-tag, but genuinely stale). Computed each package's true newest
  published SemVer directly from `npm view <pkg> versions --json`
  (mirroring `release-node.yml`'s own semver-max `latest` policy exactly,
  not inventing a new one) — all 5 resolved to `0.0.1-rc.7`.
- `npm whoami` against the fresh token succeeded (`bryant08` — a real,
  working credential, confirming the token itself is valid).
- `npm dist-tag add <pkg>@0.0.1-rc.7 latest` was attempted for all 5
  packages. **All 5 failed identically**: `npm error code EOTP — This
  operation requires a one-time password from your authenticator.`
- **No partial/inconsistent state resulted** — npm rejects the write before
  committing anything; re-queried `@agent-assembly/sdk` dist-tags.latest
  immediately after and confirmed it is unchanged (`0.0.1-rc.5`).
- Per this task's explicit security requirement, this is the exact
  "unavoidable human action" class (interactive 2FA/proof-of-presence) —
  **not bypassed**. The blocker is genuinely npm's account-level 2FA
  enforcement on registry writes for this token, distinct from (and a level
  deeper than) the original "expired token" diagnosis: even a *valid,
  working* token of this type cannot perform an unattended `dist-tag add`.
  npm's documented mechanism to avoid this for CI is an **"Automation"-type**
  access token (exempt from the 2FA-on-write prompt by design) or a
  Trusted-Publishing-covered operation — but npm OIDC does not cover
  `dist-tag add` at all (upstream `npm/cli#8547`, unrelated to token type).
  `NPM_TOKEN` was never printed, logged, or otherwise exposed during this
  attempt.
- **Exact human action required:** either (a) supply an OTP interactively
  for the 5 `npm dist-tag add` commands above, or (b) replace the
  `NPM_TOKEN` GitHub secret with an npm **Automation**-type access token
  scoped to `@agent-assembly/*` (matches AAASM-4017's own closure comment,
  which already called for "a granular automation token" — this session's
  evidence shows that specifically means the *Automation* token type, not
  merely a narrowly-scoped classic token).

### Resolution (2026-09-17, same-day follow-up)

The human completed npm interactive authentication and reported the dist-tag
updates done. **Not trusted from that report alone** — re-verified fresh
against the live public registry:

```
npm view <pkg> dist-tags --json   # for all 5 packages
```

All 5 packages: `rc` and `latest` both equal `0.0.1-rc.7`. Followed by real
clean-environment installs (explicit-version, `@rc`, and bare/default) in
fresh `mktemp -d` sandboxes for `@agent-assembly/sdk`, each resolving
`0.0.1-rc.7` and each with a real `require()`/`import` smoke test succeeding
against the actual published exports — not just a version-string check.

**Root cause fixed, not just patched**, in `node-sdk` PR #449 (merged):

- The `latest`-repair step in `release-node.yml` previously covered only
  `@agent-assembly/sdk` — never the 4 `runtime-*` sub-packages, whose
  `latest` had silently drifted to `0.0.1-alpha.4`. Now loops over all 5.
- `docs/release/npm-dist-tags.md` in `node-sdk` now documents, as a durable
  contract: the OIDC-vs-dist-tag distinction, the pre-1.0 `latest`-tracks-
  newest policy as a **deliberate decision** (evaluated against, and
  rejected, the "standard" RC-never-touches-latest convention — a rejection
  with a proven reason: this project has never shipped a GA, so that
  convention would revive the exact AAASM-3840/4730/4994 bug), how that
  policy already converges to the standard convention with no further code
  change once a GA ships, and the concrete durable fix for the recurring
  2FA/token failure (an npm Automation-type token).
- `release-validate-channels` (this repo, PR #2471, already merged) gained a
  `latest`-currency check so this class of regression cannot again slip past
  a green channel matrix unnoticed.

This is a genuinely closed loop: registry state fixed, independently
re-verified (not assumed), root cause documented, automation extended to
cover what it previously missed, and the validation gate that let 3
recurrences through is itself fixed.
